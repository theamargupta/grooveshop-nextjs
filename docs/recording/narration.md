# Narration — The Agentic Journey

Each `## NN — Title` marks one section. The prose under it is the exact spoken
script. `scripts/tts.mjs` reads this file, strips the headings, and synthesizes one
`audio/NN.mp3` per section. Every number here is verified against the repo's own
reports and `vitest list` before it was written.

## 00 — Intro

This is the story of how I rebuilt a slice of the GrooveShop storefront in Next.js — not the finished product, but the process. The interesting part of this take-home was never going to be a prettier shopping cart. It was how an AI coding workflow actually behaves when you hold it to real engineering discipline: documentation first, a failing test before any code, a production check before anything is called done. So this walkthrough follows the build the way it happened — the decisions, the model mix that wrote it, and, just as honestly, the bugs I hit and how each one was actually root-caused and fixed. Nothing here is reconstructed after the fact. The numbers come from the repository's own reports, and the mistakes are left in, because for an agentic build the recovery is the signal that matters most. There is even a log in the repository that records every meaningful prompt and what it produced, phase by phase — the idea being that for this kind of work, the prompts and the decisions behind them are as much the deliverable as the code. So treat this less as a product demo and more as a field recording of a disciplined AI build.

## 01 — The problem and the scope decision

The reference is a full GrooveShop storefront built in Nuxt: six hundred and thirteen components, eighty-two pages, eight hundred and eighty-one tests. Cloning that one to one was never the goal, and it would not have told anyone anything about judgment. So the first real decision was scope. Instead of a shallow copy of everything, I built a focused, fully tested vertical slice of the core commerce flow in Next.js sixteen with React nineteen: browse the catalog, filter it, open a product, add it to a cart, and check out. The reference did hand me one useful thing: an OpenAPI schema describing the product and category shapes. Rather than invent a data model, I used that schema as the contract for an in-memory mock data layer — real field names, realistic products, sale and out-of-stock states — so the UI was built against the same shape a real backend would return, just without the network. That keeps the slice honest: it is a front-end storefront with a typed, test-covered data layer, not a toy with hard-coded strings. One more thing shaped the scope, and it is an honesty point worth stating up front. The reference project is licensed under PolyForm Strict, not MIT. That license forbids making new works based on the software, even for learning. So I did not port their Nuxt code and I did not use their product photos. Everything here is my own code that resembles the demo, with royalty-free images. I would rather hand in an honest recreation than quietly copy something I was not licensed to copy.

## 02 — The build loop

Every feature and every bug went through the same loop, in the same order, and the order is the whole point. Documentation first: before writing a line against a library, I pull that library's own docs for the exact installed version, because recall is almost always the wrong version. A concrete example from the very first phase — the test runner refused to install because the scaffold pinned an old Node types package while Vitest needed a newer one. The fix was not to force it; it was to read the dependency resolver's own error, see which range it demanded, and bump the types package to match the actual Node runtime. The source of the fix was the error message itself, not a guess. Then research: if something breaks, I look up how other people root-caused and tested the same symptom before applying any patch. Then a spec — a short document that says what the feature does and what it refuses to do. Then a failing test, confirmed red for the right reason, because a test that has never failed has never tested anything. Then the code, until the test is green. Then the full gate: type-check, lint, unit tests, and end-to-end, all passing. Then merge, deploy, and only then verify on production. This is not a checklist I ran at the end. It is the order the work happened in, and it is enforced by hooks that block a code edit until a spec and a red test exist, and a separate gate that blocks editing after a command fails until I have actually looked something up. Those constraints are what kept an agentic workflow from drifting into confident, untested guessing — the single most expensive failure mode a coding model has. There is also a written list of things that look like proof but are not, and it is checked by name: a command printing "clean" is not proof it checked anything, a green test is not proof it actually ran, and success returned by an operation is not proof the operation changed what you expected. On an agentic build, where the thing writing the code is also the thing reporting that it worked, that skepticism is not pessimism — it is the only thing that makes the green trustworthy.

## 03 — The model mix

The build used more than one model on purpose, each in the role it is best at. Opus acts as the leader: it studies the code, writes the specs and the failing tests, reviews every change, merges it, and deploys. Codex runs in lanes and writes the implementation code. A lane is an isolated session in its own git worktree, working on a file-disjoint slice so two lanes can never touch the same file. The handoff between them is not loose. For each lane the leader writes the contract first — the spec, the shared types, and the failing tests — and only then hands the lane a plan that names exactly which files it owns. The lane writes code until those tests pass. Then it comes back, and the leader re-runs everything outside the lane's own sandbox, on the merged main, because a test that only passed in isolation has not really passed. Here is a real example from this build. After the core flow was green, three Codex lanes ran in parallel: one expanded the catalog to around forty-two products across brands and made the brand, price, and color filters actually work; one built the rich homepage; and one added the dark-mode toggle and a functional wishlist. Because the file ownership was disjoint, the leader could merge all three cleanly, then run the full test suite on the merged main to prove nothing collided. There was a real integration catch here too: when the catalog lane added new required fields to the product type, the other lanes' test fixtures no longer matched, so the leader updated those mocks at merge time rather than letting a lane paper over it. Later a second wave of two lanes added the light hero and the seven content pages. The leader never writes the feature code and the lanes never merge their own work — that separation is what makes the review real instead of ceremonial.

## 04 — Tests and coverage

Discipline only counts if it is measured, so here are the real numbers. The very first test written in this repository was a price formatter: a spec was written, then a test that expected a formatted currency string, and it failed for the right reason — the module did not exist yet. Then the module was written until the five cases passed. That tiny red-to-green cycle set the pattern every later phase followed. And the phases built on each other in a deliberate sequence: first the price formatter, then the mock data layer, then the home and listing pages, then the cart logic and product detail, then the cart and checkout pages, and only then a dedicated phase to push unit coverage up. Each phase had its own spec, its own red tests, and its own gate before the next one started — because half of three phases finished is nothing shipped, while all of one is. By the end the repository has eighty-one unit tests across twenty-two test files, and they all pass. You can list them yourself with a single Vitest command, and the video is not asking you to take the number on faith. Coverage on the unit-testable surface — the pure logic and the components — sits at about eighty-seven percent of statements and lines, against an enforced threshold of eighty percent, with the thresholds wired into the Vitest config so a regression fails the build rather than sliding by. In fact, making this very walkthrough caught a regression: a batch of new content pages had shipped without their unit tests, which had quietly pushed coverage below the threshold. The honest fix was not to lower the bar or exclude the files; it was to write the missing tests until the real number was back above eighty percent. The number you are hearing is the one after that fix. The route files are deliberately left out of that number, because they are integration surfaces: counting them under unit coverage would only pad the figure with code unit tests should not be asserting. Those routes are covered where they actually live, end to end. A Playwright suite drives the full purchase flow — home, listing, product detail, add to cart, cart subtotal, a validated checkout form, and an order-placed confirmation — asserting the visible content at every step, not merely the absence of an error. A second spec proves that checkout rejects an empty form. The happy-path run is recorded to video, so the flow can be watched, not just trusted.

## 05 — Honest debugging, part one: the image bug

Now the part that actually shows the workflow working: the bugs. The first one was the best teacher. After deploying, every product image on production rendered as blank boxes with two stray letters — "OP", "SM" — where the artwork should be. The lazy response would have been to widen a timeout or re-upload the files and hope. Instead I measured. I fetched the same image two ways, once the way a browser asks and once the way a plain client asks, and compared. That is when it surfaced: Next's image optimizer was intercepting my own local vector SVGs, and a stale optimizer cache was serving old placeholder initials instead of the real artwork. The root cause was the optimizer, not the files. The fix was to serve these particular images unoptimized — they are my own vectors, they scale losslessly, and they gain nothing from rasterizing — and to allow SVGs through a sandboxed content-security policy. A clean rebuild, a redeploy, and the artwork rendered. The lesson is the one that keeps paying off: the shape of a failure is not evidence of its cause. You measure, you disprove your first guess, and only then do you fix the layer that actually owns the problem.

## 06 — Honest debugging, part two: lint and the test selectors

Two smaller beats, because they are the kind of thing an honest build does not hide. First, lint. The cloned reference sat inside the working tree, and the linter was happily scanning tens of thousands of lines of someone else's code, drowning any real signal in noise. The honest fix was not to silence the linter; it was to exclude the vendored reference from the type-check and the lint, and to make sure that reference was git-ignored so it could never be committed or shipped. Second, the end-to-end tests. The purchase-flow spec took three fixes before it went green — and every one of them was a bug in the test, not in the application. The cart heading was an eyebrow label, not the main heading the test was looking for. The address field selector also matched "Email address", so it had to be made exact. The success message appeared three times on the page, so the assertion had to target the first. The application behaved correctly the whole time. Writing that down matters, because the tempting lie is to claim the app was broken and heroically fixed. It was not. The tests were sharpened until they asserted the right thing.

## 07 — The security audit

Before calling any of this production-ready, it got a security pass, and the results are documented rather than asserted. The dependency audit shows zero vulnerabilities in anything that ships to users. There are sixteen moderate advisories, but every one of them is in the development toolchain — the test and build machinery — which never reaches the browser or the server bundle, and they are tracked, not ignored. A grep of the source for the usual injection sinks — dangerous HTML injection, eval, raw inner HTML — comes back empty; all rendering goes through React's automatic escaping. There are no secrets in the tree, and the environment files are git-ignored. And five baseline response headers were added and then verified live with a raw header request against a production build: no-sniff on content types, frame denial, a strict referrer policy, a locked-down permissions policy, and HTTP Strict Transport Security. Client-side storage got the same scrutiny: the cart persists to local storage, but it holds only product and quantity data, nothing sensitive, and every read and write is wrapped so that a browser in private mode, or with storage blocked, cannot crash the app — it just falls back to an empty cart. The one meaningful hardening left — a nonce-based content-security policy — is written down as a documented follow-up rather than half-shipped, because a half-configured policy breaks the app. Saying what is done and what is deferred, precisely, is part of the audit.

## 08 — Production deploy and the step-eight proof

A green test suite on my machine is not proof that anything works for a user, so the loop does not end at merge. The app was deployed to Vercel production, and I confirmed the deploy by its commit hash, not by a hopeful glance at a dashboard. Then came the step that the whole discipline builds toward: driving the deployed application and checking the effect, not the absence of an error. On the live site I walked the real flow — the home page and the listing returned two hundreds, the products actually rendered, a product could be added to the cart, checkout validated and placed an order, the dark-mode toggle and the wishlist worked — and the security headers were confirmed live on the production response. One more honesty note: Vercel's deployment protection was on by default, which would have hidden the demo behind a login, so I turned it off through the API so the link is genuinely public for review. Done does not mean the code compiled. Done means I watched it work in production, as a user would, and checked that the thing I expected to change actually changed.

## 09 — The demo-match iteration and closing

The last stretch was making it look the part. The first version matched the demo's design language — the lime accent, the ink text, the Manrope type, the product cards with their sale badges and star ratings. Then, iterating against the live demo, the hero was rebuilt from a dark panel into the lighter layout the demo actually uses, the default theme was switched to light with dark available on the toggle, and seven more pages went live: wishlist, offers, a blog with article pages, rewards, about, and contact, plus the legal pages, all wired into the navigation and footer. That is where it stands: a focused, tested, deployed Next.js storefront, built through a disciplined agentic loop, with the whole prompt and process logged in the repository. And the evidence is all in the repo, not just in this narration: a coverage report, an end-to-end report with the recorded video, a security audit, and the phase-by-phase prompts log. If you want to check any claim I have made, the artifact that backs it is sitting right there next to the code. If there is one thing to take from this walkthrough, it is not the product. It is that an AI workflow becomes trustworthy exactly when you refuse to let it skip the unglamorous steps — the docs, the failing test, the measurement before the fix, and the production check before the word "done". Thanks for watching.
